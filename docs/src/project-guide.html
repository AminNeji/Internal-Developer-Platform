1. The project in one minute

Normally, a developer who needs a test environment opens a ticket and waits for someone from DevOps. This platform replaces that with a form. The developer picks a team, a type and the container images to run, and about two minutes later has a live environment at its own HTTPS address.

Three ideas make it more than a form that calls Kubernetes:

  • Git is the source of truth. The portal doesn't deploy anything. It writes a file to Git, and ArgoCD makes the cluster match. That's GitOps: every environment that ever existed is in the Git history, and any manual change in the cluster gets reverted.
  • Environments are temporary. Each has a lifetime of 1 to 72 hours, and a background job deletes it when time runs out. Forgotten environments are what make cloud bills grow.
  • The whole platform is code. Terraform creates all the AWS infrastructure, and the platform deploys itself through the same GitOps flow it offers users. It can be destroyed and rebuilt from one repository, and it was, repeatedly, to save money.

3. What happens, step by step

Creating an environment

  1. Form. Angular validates the input and posts to /api/environment/create, with the session cookie and CSRF header.
  2. ID. EnvironmentService.generateEnvId builds something like dev-payments-mw1abc: type, team, then the current time in base 36 so it's unique. Anything outside a-z 0-9 - becomes a dash, because this ID becomes a Kubernetes namespace.
  3. Values. TemplateService turns the request into YAML with SnakeYAML: the subdomain plus the list of services.
  4. Git. GitOpsService clones the dev branch with JGit into a temp folder, writes environments/<id>/values.yaml, commits and pushes.
  5. ArgoCD. ArgoCdService POSTs an Application to ArgoCD's REST API: use the chart at charts/environment, with that values file, in a namespace named after the ID, syncing automatically.
  6. Database. The environment and its services are saved in Postgres, with expiresAt set to now plus the TTL.
  7. Cluster. ArgoCD renders the chart and applies it. Kubernetes starts the pods.
  8. Load balancer. The AWS Load Balancer Controller sees the new Ingress and adds a rule for its host to the shared ALB. Because the ALB already exists, this takes seconds. A new ALB would take 2 to 3 minutes.
  9. DNS. ExternalDNS sees the Ingress and creates the Route 53 record.
  10. Status. The detail page polls /status every 5 seconds until ArgoCD says Healthy or Degraded, then shows the URL.

When a create fails

Git and ArgoCD can't take part in a database transaction, so createEnvironment rolls back by hand. If the ArgoCD call or the database save throws, it deletes the ArgoCD app and the Git folder, then reports the original error. Each undo step runs even if the other fails. Without this, you'd get an environment running in the cluster that the portal doesn't know about, so nobody could see it or destroy it.

Destroying an environment

  1. Delete the ArgoCD Application with cascade=true, which removes its workloads from the cluster. A 404 counts as success.
  2. Delete the folder from Git. If it's already gone, nothing happens.
  3. Delete the database row, last on purpose. If step 1 or 2 fails, the row survives and the destroy can be repeated.

The controller then removes the environment's ALB rules, and ExternalDNS removes its DNS record. The empty namespace stays behind, because ArgoCD doesn't delete namespaces it created with CreateNamespace=true. It costs nothing, and goes away with the cluster.

Expiry

CleanupService.destroyExpired runs every 5 minutes (@Scheduled), finds rows with expiresAt in the past and calls the same destroy as the button. Each destroy has its own try/catch, so one failure doesn't block the others, and the surviving row gets retried next time. Both backend replicas run this job. That's safe because every destroy step can be repeated, so the worst case is one replica logging a harmless error.

Deploying a change to the platform

  1. You push to dev. GitHub Actions builds, tests and scans.
  2. It builds both Docker images and pushes them to ECR, tagged with the commit SHA.
  3. It edits the image tag in k8s/backend/deployment.yml and k8s/frontend/deployment.yml using yq, and commits that with [skip ci] so it doesn't trigger itself.
  4. ArgoCD sees the change (it checks every 3 minutes) and does a rolling update.

CI has no access to the cluster at all. It only has rights to ECR and to the repository. That's the "pull model" of GitOps.

6. The Helm chart

charts/environment loops over .Values.services and renders a Deployment and Service per service, plus one Ingress with a path per service. This is what the backend writes for one environment:

ingress:
  host: dev-payments-mw1abc.idplatform.tech
services:
  - serviceName: api
    image: nginx:alpine
    port: 80
    path: /
    healthPath: /
    env:
      LOG_LEVEL: info

The chart's own values.yaml supplies the rest: 1 replica, the ALB group name and the certificate ARN. Test it without a cluster:

helm template test charts/environment -f charts/environment/ci/test-values.yaml

The chart replaced an earlier FreeMarker version that generated raw manifests. Now the templates live in one versioned place and each environment contributes only its data.

7. GitOps and ArgoCD

There are two kinds of ArgoCD Application:

  • idp-platform deploys the portal itself from k8s/. It's applied by hand once, per cluster.
  • One per environment, created by the backend through the API. Each uses the Helm chart with its own values file.

Both track the dev branch with automated sync, prune (things removed from Git get removed from the cluster) and selfHeal (manual changes in the cluster get reverted). That's why deleting a Deployment by hand doesn't stick: ArgoCD puts it back.

The backend logs in as a dedicated account, idp-backend, defined in terraform/argocd.tf. Its API key has no expiry, and its rights cover Applications only. It can't, for example, add repositories.

8. Login and security

How login works

  1. Angular calls /api/me. A 401 means nobody is signed in, so it shows the sign-in screen.
  2. The button navigates to /api/oauth2/authorization/github. Spring redirects the browser to GitHub.
  3. The user approves. GitHub redirects back to /api/login/oauth2/code/github with a one-time code.
  4. Spring swaps the code for an access token and fetches the profile.
  5. AllowedUsersService checks the username. If it isn't listed, the user lands on /?denied.
  6. Spring creates a session and sets a SESSION cookie.

Compared with JWT

JWTThis project (server-side session)
The token holds the user's data and is signedThe cookie holds only an ID. The data is in Postgres.
Hard to revoke before it expiresDelete the row and the user is signed out
JavaScript has to store and send itThe browser sends it automatically, and JavaScript can't read it
No CSRF risk when sent in a headerNeeds CSRF protection, because cookies are sent automatically

Sessions are in Postgres because there are 2 backend replicas. A session kept in one pod's memory would be lost as soon as the load balancer sent the next request to the other pod.

CSRF

Spring sets a readable XSRF-TOKEN cookie. Angular's HttpClient copies it into an X-XSRF-TOKEN header on POST and DELETE. Another website can make the browser send cookies but can't read them, so it can't produce that header.

Permissions in AWS

Controllers that need AWS access use IRSA: an IAM role tied to one Kubernetes service account, with temporary credentials and no stored keys. There are three: idp-alb-controller, idp-ebs-csi and idp-external-dns. ExternalDNS can only change this one hosted zone.

Secrets

k8s/secret.yml, k8s/database/secret.yml and .env are gitignored and applied by hand. ArgoCD deploys everything in k8s/ from Git, and since these aren't in Git, it never sees them. A step up would be Sealed Secrets or External Secrets.

9. Networking and DNS

The network: one VPC with public and private subnets in 2 availability zones. Nodes sit in private subnets, and the load balancer in public ones. Outbound traffic from nodes goes through one NAT gateway, which is cheaper than one per zone but is a single point of failure.

The path of a request: browser → Route 53 → ALB (HTTPS with the ACM certificate) → directly to the pod's IP (target-type: ip), skipping NodePorts.

One shared ALB. Each Ingress normally creates its own ALB, at about $16 to $18 a month each. Giving them all the annotation alb.ingress.kubernetes.io/group.name: idp-shared merges them into one, and each Ingress only adds rules. Settings like scheme, ports and redirect must match across the group, so k8s/ingress.yml and the chart use the same values.

Rule order matters. In the portal's Ingress, /api is listed before /, because / matches everything.

Health checks. Each Service sets its own check path with an annotation. The backend uses /actuator/health, which is public. Redis is excluded from that check, because the cluster has no Redis host and it would report DOWN (503). If all targets are unhealthy, an ALB "fails open" and sends traffic to them anyway, so a broken health check can look like it's working.

The certificate. One ACM certificate covers idplatform.tech and *.idplatform.tech. It's kept outside Terraform so it survives a destroy.

ExternalDNS. It watches Ingresses and creates or removes records, with a TXT record marking each one as its own. It never touches records it didn't create. That's why a hand-made record has to be deleted once before it can take over that name.

13. Limits and costs

What it doesn't do

  • Secrets: environment variables are stored in plain text in a public repository. Don't put passwords in them. The form warns about this.
  • Quotas: nothing limits how many environments a team creates.
  • Cluster size: 3 t3.small nodes allow 33 pods in total, and the platform itself uses about 28. Only about 4 or 5 environment services fit at once. Beyond that, pods stay Pending. Change instance_types or desired_size in eks.tf for more, within the account's limit of 8 vCPUs.
  • Editing: an environment can't be changed, only destroyed and recreated.
  • Environment database: deployed apps can't request a database.
  • Monitoring: only ArgoCD's health status. No metrics, log search or alerts.
  • Terraform state: local, so only one person can safely run it.
  • Debug port: the backend image starts with a debug agent on 5005. No Service exposes it, but it should be removed from the production image.
  • Unused resources: Redis costs about $13 a month while running and nothing uses it. Remove elasticache.tf, security-groups.tf and its output when you want to save that.
  • Old folders: environments/ holds values from before destroy started cleaning up. They do nothing and can be deleted.

15. Questions you'll be asked

Why GitOps instead of having the backend call Kubernetes?

Git gives a full history of every environment, a simple way to roll back, and self-repair: ArgoCD reverts drift. The backend also never holds cluster credentials, so a compromised backend can't run arbitrary things on the cluster directly. The trade-off is that creates depend on Git and are slower.

What happens if ArgoCD goes down?

Running environments keep running, since ArgoCD only reconciles. New creates fail at the ArgoCD call and roll back their Git commit. When ArgoCD returns, it catches up from Git.

What if the backend crashes in the middle of a create?

The rollback code only runs if the process is alive, so a crash between steps can leave a Git folder or an ArgoCD app with no database row. A fuller design would write the intent to the database first and have a job reconcile it. The TTL job doesn't catch this today, since it works from database rows.

Why do both replicas run the cleanup job, and isn't that a problem?

Every step of destroy can safely be repeated, so running twice causes at most a logged error. For heavier jobs I'd add a lock such as ShedLock.

Why sessions and not JWT?

The browser is the only client, sessions can be revoked at once, and Spring Security provides them out of the box. The cost is CSRF protection and a shared store, so Postgres holds them for both replicas.

How do environments stay isolated from each other?

Separate namespaces, which separate names and resources. They aren't a security boundary without NetworkPolicies, so pods can still reach each other across namespaces. I'd add default-deny NetworkPolicies and ResourceQuotas next.

How would you scale this to many teams?

Quotas per team, cluster autoscaling (Karpenter), remote Terraform state with locking, secrets from a vault, and monitoring. Git pushes become a bottleneck under heavy use, so I'd queue them, and perhaps give environment values their own repository.

What was the hardest part?

Things that fail quietly. JGit doesn't throw on a rejected push. An ALB fails open, so a broken health check looks fine. --legacy-peer-deps hid a missing dependency until the first production build. Each was found by running against real infrastructure, not by unit tests.

How much does it cost, and how did you control that?

About $7 a day while running. Environments expire automatically, they share one load balancer, Postgres runs in the cluster instead of RDS, and the whole stack can be destroyed and rebuilt from code when it's not needed.
